# Artefacts

`<app> generate-artefacts --output-dir ci/` writes the files CI needs
to build and deploy the service. Contract in, artefacts out.

Subcommand: the `cli` feature's `StandardCommand::GenerateArtefacts`
([../../src/cli/commands.rs](../../src/cli/commands.rs)).

---

## What gets written

`generate-artefacts` writes top-level files only:

```text
ci/
|-- metrics-manifest.json        # when `metrics` feature on
|-- deployment-contract.json     # when ServiceApp::deployment_contract() is Some
|-- container-manifest.json      # minimal CI-consumable subset
|-- Dockerfile.runtime           # runtime-stage fragment for CI composition
|-- config-schema.{json,yaml}    # when the contract carries config_schema
`-- capability-catalog.{json,yaml}  # when the contract carries capabilities
```

scalo writes no Helm chart. A chart assembler turns `deployment-contract.json`
into a thin chart on the [scalo-service](../../charts/scalo-service/README.md)
library chart, which renders every Kubernetes object from the contract -- see
[Kubernetes objects](#kubernetes-objects) below.

---

## File-by-file

### `metrics-manifest.json`

Full metric catalogue: every counter, gauge, histogram, with names,
types, labels, bucket boundaries. It is the scalo runtime set --
`ServiceMetrics`, app info, and the worker pool and batch engine sets
when compiled in -- plus whatever the app's `register_metrics()` adds,
each name once and under the `metrics.namespace` the service's own
config sets. CI uses it to check that Prometheus dashboards and alerts
reference real metrics. Byte-identical to `metrics-manifest` on stdout.

It lists what the scalo registry describes, which is not yet everything
the service serves: the `process_*`, `container_*`, `http_client_*` and
memory guard gauges are on `/metrics` but not in the manifest
(scalo-rs#137).

```json
{
  "schema_version": 1,
  "app": "my-app",
  "namespace": "",
  "metrics": [
    { "name": "transport_sent_total", "type": "counter", "labels": ["transport", "path"], ... }
  ]
}
```

### `deployment-contract.json`

The serialised `DeploymentContract`, schema version 4. CI reads it to
know what to validate against, and a chart assembler turns it into a thin chart
on the [scalo-service](../../charts/scalo-service/README.md) library chart. Its
JSON Schema is `charts/scalo-service/schema/deployment-contract.v4.schema.json`,
derived from the contract types -- see [contract.md](contract.md#the-json-schema).

### `container-manifest.json`

Minimal subset of the contract that CI needs to build the image:
base image, registry, runtime packages, exposed ports, healthcheck,
labels. No secrets, no K8s-specific config. A port gated with `when` is
not in `expose_ports`; it is listed under `conditional_ports` with its
condition, a key that appears only when some port is gated (see
[contract.md](contract.md#ports)). In `expose_ports` a TCP port is a bare number and a UDP port is the string `"514/udp"`, the form the Dockerfile `EXPOSE` line uses.

Produced by `generate_container_manifest(&contract)`. Schema version
`"1"` (string, separate from the contract schema).

### `Dockerfile.runtime`

Runtime-stage fragment of a multi-stage Dockerfile, produced by
`generate_runtime_stage(&contract)`. CI composes the full Dockerfile
by prepending its own builder stages (cargo-chef pattern) and
appending this fragment. Boundary: scalo owns what's *in* the
container, CI owns how to *build* the binary.

Generated for a contract with the `transport-kafka` and `spool` features on the default base image:

```dockerfile
# --- Runtime stage (generated by scalo deployment contract) ---
FROM debian:trixie-slim@sha256:62bd423aeee912639ca8ee681c2b762cb3e25137e0a92b20be455898a9f034ad AS runtime

# Static OCI labels (from contract)
LABEL org.opencontainers.image.title="my-app"
LABEL org.opencontainers.image.description=""
LABEL io.scalo.profile="production"

# Apt versions are unpinned because Debian drops superseded ones, so the digest-pinned base is what fixes the release.
# hadolint ignore=DL3008
RUN apt-get update && apt-get install -y --no-install-recommends \
    ca-certificates \
    && rm -rf /var/lib/apt/lists/*

# Dynamic OCI labels (injected by CI at build time)
ARG OCI_SOURCE=""
ARG OCI_REVISION=""
ARG OCI_VERSION=""
ARG OCI_CREATED=""
LABEL org.opencontainers.image.source="${OCI_SOURCE}"
LABEL org.opencontainers.image.revision="${OCI_REVISION}"
LABEL org.opencontainers.image.version="${OCI_VERSION}"
LABEL org.opencontainers.image.created="${OCI_CREATED}"

# The builder stage is prepended by CI, so this fragment cannot define it.
# hadolint ignore=DL3022
COPY --from=builder /app/target/release/my-app /usr/local/bin/my-app
RUN chmod +x /usr/local/bin/my-app

# A base image may ship its own user at UID 1000 (Ubuntu's `ubuntu`), so remove it first.
RUN if id ubuntu >/dev/null 2>&1; then userdel -r ubuntu; fi && useradd --create-home --uid 1000 appuser
WORKDIR /home/appuser
# Numeric, so Kubernetes runAsNonRoot can verify it without reading /etc/passwd.
USER 1000

EXPOSE 9090

# bash builtins only, so the image needs no HTTP client. A status other than 200 exits 1.
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
    CMD ["bash", "-c", "exec 3<>/dev/tcp/localhost/9090 && printf 'GET /livez HTTP/1.0\\r\\n\\r\\n' >&3 && read -r _ code _ <&3 && [ \"$code\" = 200 ]"]

ENTRYPOINT ["my-app"]
CMD ["--config", "/etc/my-app/config.yaml"]
```

`FROM` is the contract's `base_image`. The default, `DEFAULT_BASE_IMAGE`, is `debian:trixie-slim` pinned to its multi-arch index digest, and Renovate moves the digest. Override it with `deployment.base_image`.

The sample contract names no vendor or licence, so the fragment carries no `org.opencontainers.image.vendor` or `org.opencontainers.image.licenses` label. Set `oci_labels.vendor` and `oci_labels.licenses` and the two lines appear after `description`, vendor first. `io.scalo.profile` is under the contract's `oci_labels.label_namespace` -- see [contract.md](contract.md#labels).

The `userdel -r ubuntu` before `useradd --uid 1000 appuser` is guarded by
`id ubuntu` because it is only needed on an Ubuntu 24.04 base, which ships
a `ubuntu` user already squatting UID 1000 - `useradd --uid 1000` fails
unless it is removed first. Debian trixie slim has no such account, so the
guard makes the line a no-op there rather than a build failure.

`USER` is numeric because Kubernetes `runAsNonRoot` can only verify a numeric user. The uid still resolves to `appuser`: `id` in the image prints `uid=1000(appuser) gid=1000(appuser)`.

The process starts in `/home/appuser`, which `useradd --create-home` gives to appuser, so a relative path the app writes lands somewhere it owns. A contract with `writable_paths` gets one more line before `WORKDIR`, which creates each path and hands it to appuser while the build still runs as root:

```dockerfile
RUN mkdir -p '/var/spool/my-app' '/var/data/my-app' && chown 1000:1000 '/var/spool/my-app' '/var/data/my-app'
```

A production image carries `ca-certificates`, any runtime packages the contract lists and the binary. The Kafka transport and the spool link their C libraries statically, so the sample installs nothing else ([native-deps.md](native-deps.md)). `curl` and `gnupg` are there only to import a custom repo's signing key, and the same `RUN` purges them once the repo's packages are in. The healthcheck speaks HTTP with bash builtins, so it needs no client. A development image (`with_dev_profile`) keeps `curl`, `netcat-openbsd` and `iputils-ping` beside the diagnostic tools.

All four generators run [`DeploymentContract::validate`](contract.md) first and return its error, so a contract the chart would refuse renders no Dockerfile, runtime stage, compose fragment or container manifest either.

The generated Dockerfile and fragment lint clean under hadolint, which gates the build. Three findings are suppressed at the instruction they concern, each with its reason on the line above:

| Rule | Instruction | Why it is suppressed |
| --- | --- | --- |
| DL3008 | the `apt-get install` RUN | Debian's archive drops superseded package versions, so a pinned version breaks the build within weeks. The digest-pinned base fixes the release. |
| DL3025 | `HEALTHCHECK` | Shell form lets `\|\| exit 1` map any curl failure onto 1, the only unhealthy status Docker defines. Exec form cannot. |
| DL3022 | `COPY --from=builder` (fragment only) | CI prepends the builder stage, so the fragment cannot define it. |

The pragma only works on the line directly above its instruction, so nothing goes between the two.

Dynamic OCI labels (`source`, `revision`, `version`, `created`)
arrive via `--build-arg` from CI at build time.

### Kubernetes objects

The [scalo-service](../../charts/scalo-service/README.md) library chart renders
them from `deployment-contract.json`: the Deployment, Services, ConfigMaps,
ServiceAccount, claims, disruption budget, KEDA ScaledObject and
TriggerAuthentication, fallback HPA and NetworkPolicy. Its README lists what
each contract field and value renders, and how to assemble the thin chart a
service ships.

To preview a service's chart locally, assemble it from the contract with a
chart assembler such as `hyperi-ci chart assemble --image <repo>:<tag>@sha256:<digest>`,
then run `helm dependency build` and `helm template` on the directory it prints.

## Autogenerated header

Every generated file starts with:

```text
# AUTOGENERATED -- do not edit by hand.
# Generated by scalo::deployment::generate_dockerfile()
# Schema version: 4
# Source contract: my-app::deployment::contract()
# Regenerate by calling scalo::deployment::generate_dockerfile() on that contract.
```

No scalo subcommand writes the full Dockerfile. `generate-artefacts` writes `Dockerfile.runtime`, the runtime stage CI composes.

A generated Dockerfile puts `# License:` and `# Copyright:` lines above that block, each only when `oci_labels.licenses` or `oci_labels.copyright` is set.

- **Do not edit** -- edits get clobbered on the next CI regeneration.
- **To change behaviour, change the contract.** The contract is the
  source of truth; generated files are reports.

## Drift detection in CI

CI regenerates into a scratch directory and diffs against committed `ci/`:

```bash
mkdir -p /tmp/fresh && ./target/release/my-app generate-artefacts \
    --output-dir /tmp/fresh
diff -r /tmp/fresh ci/   # zero output -> no drift
```

Any diff fails the build, forcing regenerate-and-commit so deployment
artefacts always match the binary that ships.

`validate_dockerfile()` is the programmatic alternative when a committed
Dockerfile carries intentional deviations (e.g. CI's prepended builder
stages). It returns the list of `ContractMismatch`es rather than a hard diff.

## Determinism

Identical input gives byte-identical output -- no timestamps, no
random IDs. Two consecutive runs match exactly. This is what makes the
CI diff check reliable.

The input is more than the source. `generate-artefacts` loads the app's
config first, once, and every artefact follows that cascade: the
contract's base image and registry, and the metrics namespace. So a dev
box and CI with different settings files or env
vars can generate different artefacts from one commit. A config that
does not load is reported on stderr and the defaults are taken. The
manifest's `version` and `commit` also change with each build.

A contract with a `default_config` listener no port declares is refused
before anything is written -- see [contract.md](contract.md#ports).
